1The short version

WELA reads a PC's Windows event logs and answers four questions for every power cycle with fixed, written-down rules. Every answer shows its evidence, what was expected but not logged, and how strong it is.

Design principles

  • Rules, not a trained model. The same logs always give the same answer. Every event ID, weight and time window lives in one catalogue file (wela/catalog.py) and is pinned by automated tests.
  • Evidence-weighted. Each event Windows writes when a PC stops carries a weight; the confidence is the sum of what was found, minus penalties for contradictions and log gaps.
  • Redundant signals. Windows records one stop several times, in different logs and by different components. WELA reads all of them, so one lost event does not change the answer — it only lowers the score.
  • Honest about gaps. When the logs cannot show something, WELA says Undetermined or Can't tell rather than guess. Missing records, cleared logs and clock changes are detected and lower confidence.
  • Explainable. Every verdict lists the events behind it, each one clickable to its raw data.
  • Local only. Runs on the engineer's PC, serves the UI on 127.0.0.1 and makes no network calls; the logs never leave the machine.

2From log files to one timeline

Every event, from every log, becomes one record on one UTC timeline. Each record is then tagged with what it means.

Which logs, and what each contributes

LogWhat WELA takes from it
SystemPower-cycle events (12, 13, 41, 109, 1074, 6005, 6006, 6008 …), disk / NTFS / NVMe driver events, service failures, display-driver timeouts, Windows Update
ApplicationApp crashes and hangs, Windows Error Reporting (including blue-screen reports), installer events
Storage-Storport / Operational (+ Health)Per-request storage problems — timeouts, resets, retries — often with the drive's vendor, product ID and serial
Partition / Diagnostic (optional)The drive inventory at each boot: model, serial, firmware, disk number — turns "Disk 1" into a named drive

From a folder (e.g. a copy of C:\Windows\System32\winevt\Logs, which holds hundreds of logs) only System, Application and Storport are read and the rest are counted as skipped; a file given by itself is always read.

Reading and normalising

  • .evtx files are read on Windows with the built-in wevtutil — Windows renders its own events, so field names and values are exactly what Windows stored. Fallbacks: PowerShell Get-WinEvent, then the optional python-evtx package on other systems. XML exports are read too.
  • Every event becomes one record: time (UTC), log, provider, event ID, record ID, level (1 critical · 2 error · 3 warning · 4 information) and its data fields (named fields, or param1…n when Windows does not name them).
  • All logs are merged into one timeline sorted by time (System first at equal times, then record ID). Why UTC: logs from different time zones or across daylight-saving changes line up; the UI converts to the chosen zone.

Three meanings per event

MeaningExampleUsed for
Power signalKernel-Power 41 → "Unclean shutdown reported"Classification and its confidence (ch. 4–5)

Matching is by provider + event ID from the catalogue, so the rules work on meanings and there is one place to change them. A wela_config.json next to run_wela.py overrides any part of the catalogue without touching code.

3Boots, sessions and time windows

Every boot closes the session before it. WELA finds the boots, then asks of each one: how did the session before it end — and what was happening around that moment?
  • A boot = Kernel-General 12, EventLog 6005 / 6009 and Kernel-Boot 27 within 180 s of each other. Any one of 12 or 6005 is enough (or 27 with BootType 0 / 1), so a boot is found even when a marker is missing. Kernel-Boot 27 BootType 1 = a Fast Startup boot; BootType 2 = a resume from hibernate, which is not a boot.
  • A session = everything between two boots. The last sign of life = the last event of any log before the next boot — the anchor for a hard shutdown, because a power loss writes nothing at the moment it happens.
  • Sleeps inside a session are rebuilt from Kernel-Power 42 (enter) and 107 (resume), Power-Troubleshooter 1 (sleep / wake times and wake source), 506 / 507 (Modern Standby) and Kernel-Boot 27 BootType 2 (hibernate resume). Any one of them is enough to rebuild an episode.
WindowLengthReadsWhy this length
Stop signalslast 30 min before the last sign of life1074, 13, 6006, 109, 7002An orderly shutdown writes them within seconds to minutes; 30 min tolerates slow shutdowns such as update installs.
Hard signalsfirst 15 min after the boot41, 6008, 1001Windows writes them while booting; the crash report (1001) can follow minutes later, once the dump is processed.
Drive60 s before the last sign of life (to +5 s) and 60 s after bootevery storage event, every levelA drive fault that brings a PC down shows seconds before it (demo: resets 32 s and 17 s before). A wider window pulls in unrelated noise.

4How a power cycle is classified

The order of the checks is the design. Windows' own report of an unclean stop beats everything; then a clean stop; only when both are absent does WELA infer — and it says so.

Why hard signals come first: a PC can log a clean stop and still lose power before it finishes. Kernel-Power 41 is written by the kernel at the next boot, when it finds the previous stop was not completed — it is Windows' own after-the-fact verdict, so it outranks anything written beforehand. When both appear, the power cycle is a hard shutdown with a conflict penalty (chapter 5).

Hard-shutdown subtype — read from the fields of event 41 (first match)

EvidenceSubtypeWhat it means
BugcheckCode ≠ 0, or a 1001 crash reportCrash (bugcheck 0x…)Windows stopped with a blue screen; the code says why (chapter 7)
PowerButtonTimestamp ≠ 0Power button long-pressSomeone held the power button — usually because the PC had stopped responding
SleepInProgress ≠ 0, or a sleep never resumedPower lost during sleep / hibernateBattery drained or power cut while asleep
Stop events logged, then 41Shutdown started but did not complete (hang)The shutdown hung on the way down

Restart or shutdown?

  1. The 1074's shutdown type (param 5), matched in English, German, French, Spanish, Italian, Dutch, Japanese, Chinese, Korean and Russian.
  2. The next boot is a Fast Startup boot (Kernel-Boot 27 BootType 1) → shutdown (Fast Startup: the kernel hibernated).
  3. Otherwise the stop-to-boot gap: under 5 min → restart, else shutdown — flagged "inferred from gap".
  4. A 1074 that says restart but a boot more than 30 min later → warning, needs review.

5The confidence percentage

Confidence = how much of the evidence Windows normally writes for this kind of ending was found, minus penalties for contradictions and log gaps. It is an evidence score on a 0–100% scale — not a statistical probability.

Why these numbers

  • By how directly the event records the ending. 41 is the kernel's own verdict at the next boot (0.50). 6008 comes from a different component — the event log service noticing it was not closed cleanly — so it is independent confirmation (0.40). A crash report confirms a crash, but not every hard stop is a crash (0.20). On the clean side, 1074 is the request itself (0.35); 13 and 6006 are the kernel's and the event log's last clean words (0.30 each); 109 shows the shutdown started, not that it finished (0.20); a logoff also happens without any shutdown (0.05).
  • So that one weak signal never passes review, and two independent ones do. The review line is 60%: 1074 alone 45% · 13 alone 30% · 1001 alone 50% — review; 13 + 6006 = 60% · 6008 alone 70% · 41 alone 80% — pass (both hard cases include the +0.30 for a silent end).
  • Capped at 100%: once the expected evidence is all there, more of it adds no certainty.
  • Hand-set, not fitted. There is no labelled set of claims to fit them to yet; they were set from how Windows writes these events and checked against the demo cases. They live in catalog.py, can be tuned without code, and calibration on 20–30 closed claims is the next step.

"Needs review", colours and sleeps

  • Needs review = confidence below 60% (review_threshold) or any warning: a conflict, a record gap, an inferred ending, a restart that took over 30 min, a sleep without resume.
  • Colour of the percentage in the UI: ≥ 80% green · 60–79% blue · 35–59% amber · below 35% red.
  • Sleeps score by how many of their three signals were found — 42 enter, 107 resume, Power-Troubleshooter 1 (or 27 BootType 2 for a hibernate): none 30% · one 60% · two 85% · three 100%. Modern Standby: 90% with both 506 and 507, else 50%. A sleep that never resumed: at most 50%. Demo: S2 (entry not logged) 85%, S3 (Power-Troubleshooter only) 60%, S4 (never resumed) 50%.

6How Storport and disk events are judged

Each storage event gets a label and a state. The worst state in the minute before the last sign of life decides the drive verdict. Informational events are listed with their fields but never counted.

What Storport is. Storport is Windows' storage port driver. It sits between the disk / file-system layers and the drive's own driver (stornvme for NVMe, storahci for SATA). Its Operational log records problems with individual I/O requests — timeouts, resets, retries, latency — and usually names the drive (vendor, product ID, serial), which makes it the best log for tying a fault to a specific drive.

How a state is assigned (first match)

  1. Known provider + event ID in the catalogue → a fixed label and state (table below).
  2. Any other event in a Storport log → state from Windows' own severity: Critical or Error → error, Warning → warning, Information → info (listed, never counted).
  3. Any other event from a storage provider (name contains stornvme, storahci, storport, nvme, iastor or disk) at Critical, Error or Warning level → state from its severity.
Why severity for Storport. Microsoft does not publish a meaning for each Storport Operational event ID, so WELA does not invent one: it uses the severity Windows itself gave the event. Information-level events still appear in the drawer with their key fields (opcode, status, sense data, latency …) so the engineer can read them. Naming the Storport IDs that matter, from real claim logs, is on the roadmap.

Two refinements

  • Platform vs. drive. WHEA-Logger events report errors in the CPU, PCIe or memory platform — not necessarily in the drive. They stay in the window, but are left out of the drive state, so on their own they can make "Did the drive cause it?" at most Possibly, never Likely.
  • Readable commands. NVMe I/O is translated to SCSI commands by stornvme, so Storport events carry SCSI opcodes. WELA decodes them (e.g. 0x2A WRITE(10), 0x35 SYNCHRONIZE CACHE(10), 0x28 READ(10)) so the engineer can see which command failed.

Why these codes. The "strong" ones mean Windows could not read from or reach its disk (in-page errors, boot device or volume gone) or a critical process was killed — commonly by failed I/O. The "sometimes" ones are often storage-related (a storage driver stuck in a power transition or a DPC) but have other causes too.

Effect on the drive — the 60 s after boot: Drive missing after boot (157) · Errors (reset / error) · Warnings (slow / warning, or platform only) · Healthy · No data. A drive that is missing or erroring after the boot supports a drive cause.

"No drive evidence" is not "healthy". Windows keeps its logs on the system drive. If that drive froze instantly, its last events were never saved — a failing drive can look quiet. WELA says this on every such verdict and asks for the drive's own SMART and error logs.

8Which drive — is it Samsung's?

Every storage event is tied to a physical drive where the logs allow it, and WELA says how sure it is: named and disk number are certain; only drive is marked "probably".
MethodHowShown as
NamedThe event carries the drive's identity: Storport VendorId / ProductId / SerialNumber, a Partition model, or a PCI vendor ID (VEN_xxxx) in a device pathSamsung drive — sure
Disk numberThe event names \Device\HarddiskN; the Partition inventory of that same boot says which drive was disk N (numbers can change between boots, e.g. when a USB drive is plugged in)Samsung drive — sure
Only driveThe event names no drive, but that boot (or the whole log) has only one drive, and the event does not point at another disk numberProbably the Samsung drive
Not identifiedNone of the above. WHEA platform events are never guessed — their PCIe device can be anythingDrive not identified
  • Samsung is recognised by the word "Samsung" anywhere in the event, PCI vendor ID 144D, or a Samsung part number (MZ…, e.g. MZVL2512HCJQ) in a model or product field. Generic vendor strings ("NVMe", "ATA", "SCSI") are ignored.
  • Twelve vendors are known (Samsung, Western Digital / SanDisk, SK hynix, Kioxia / Toshiba, Micron / Crucial, Intel / Solidigm, Seagate, Kingston, Phison, Silicon Motion, ADATA, Lite-On), so another drive is named rather than just "not Samsung". Intel and AMD PCI IDs are left out on purpose: they also name the CPU's own PCIe ports.
  • One drive, two serial formats (the serial vs. the NVMe EUI-64 some Windows builds report) are merged into one drive.
  • The highlighted vendor is a setting (highlight_vendor); Samsung is highlighted in teal everywhere — UI, timeline, HTML and Excel.

9How apps, updates and services are singled out

Four steps: tag the events that matter, read only the right stretch of time, read who asked for the shutdown, then take the strongest explanation first. A request on record beats circumstantial events; a system-process crash beats an ordinary app crash.

Step 1 — which events count

Each event also gets its subject — the app (e.g. explorer.exe), the update (KB number), the installed product or the service — which is what the reasons name.

Step 2 — the stretch of time

The verdict reads the 15 min before the last sign of life and the 10 min after the boot — but never back past the boot or wake that ended the previous power cycle, and never on past the next power-off. If the previous power cycle was only 30 s earlier, it reads those 30 s ("… in the 30s since T33 boot"): anything before belongs to that earlier power cycle. The lists under the verdict show everything between the power cycles; problems older than the 15 min are summed up, e.g. "Earlier, since T7 boot: Crash report: blue screen x1".

Step 3 — who asked? The 1074 record

User32 1074 is Windows' own record of a shutdown or restart request: param 1 the process, 3 the reason text, 4 the reason code, 5 the type, 6 a comment, 7 the user.

The process → a category, first matching path fragment wins:

  • Windows Update — TrustedInstaller, TiWorker, MoUsoCoreWorker, UsoClient, wuauclt, SetupHost …
  • OEM / vendor tool — Dell (dcu-cli, SupportAssist), Lenovo, HP, Samsung Magician, firmware / BIOS updaters
  • IT management — SCCM (CcmExec), Intune (OmaDmClient, IntuneManagementExtension, AgentExecutor), Group Policy scripts
  • Installer — msiexec, *setup*, *install*; script — shutdown.exe, PowerShell, cmd
  • System — wininit, lsass, csrss; user — Explorer, RuntimeBroker, Start menu, Winlogon, LogonUI

The reason code → decoded from its bits — the same in every Windows language: bits 16–23 major reason, bits 0–15 minor reason, top bit = planned.

CodeDecodes to
0x80020003planned · Operating System: Upgrade → Windows Update
0x00050006unplanned · System: Unstable → system unstable
0x00000000unplanned · Other — a typical user shutdown

When process and code disagree, the code wins for updates: "Update and restart" from the Start menu is asked by the shell, but the code says OS servicing → Windows Update. A system process with an "unstable" code or a "terminated unexpectedly" comment → System process crash.

Why this order and these weights

  • 1074 (0.70, Confirmed): Windows' own record of who asked — the only direct evidence. The reason code agreeing and backing events (+0.15 each) take it to 100%.
  • "Restarts the PC" events (0.60, Likely): the component says it is restarting the PC, but without a 1074 the request itself is not on record — so Likely, never Confirmed.
  • System process crash (0.50, +0.20): Windows is built to stop when csrss, wininit or lsass die (crash codes 0xEF / 0xF4) — a direct chain; with the matching code it becomes Likely.
  • Unfinished update (0.40): power lost mid-install is a known risk, but the update may only have been running at the time.
  • Hang (0.35): a PC that stops responding is often forced off with the power button — it fits the long-press subtype.
  • Display driver (0.30): graphics-driver timeouts often come just before a freeze.
  • App crash (0.25): an ordinary app crash cannot take Windows down by itself — it shows what was failing at the time. That is why App crashed is never more than Possibly.
  • Symptom check (−0.15): a drive that stalls makes apps hang and crash. When the drive was also failing, the software events are more likely effects than causes, and the reason says so.

13Questions to expect

Does 100% confidence mean it is certain?No. It means all the evidence Windows normally writes for that kind of ending is there and nothing contradicts it. It is an evidence score, capped at 100%, not a probability. Calibration on closed claims is the next step.
Where do the weights come from?From how directly each event records the ending: the kernel's own 41 (0.50) above the event log's 6008 (0.40) above a crash report (0.20). They are set so one weak signal stays under the 60% review line and two independent ones pass. They are in the catalogue and can be tuned without code.
How do you know it is right?52 automated tests pin every rule, including a demo case of 16 power cycles and 5 sleeps with known answers and a random-input test. Validation on 20–30 closed claims and lab tests is next.
Could it wrongly blame our drive?"Likely" needs a reset, error or missing-drive event on the drive in the minute before power-off, or a crash code that points at storage. Platform (WHEA) errors alone stop at Possibly; orderly shutdowns are never blamed; undetermined ones are held back a step. And it says whose drive it was.
Could it miss a drive fault?Yes, if the system drive froze before writing its last events. That is why a quiet minute is "No drive evidence", not "healthy", and why every such verdict asks for SMART data.
Why 60 seconds for the drive?Faults that bring a PC down show up seconds before it (in the demo, 32 s and 17 s). A wider window pulls in unrelated noise. It is a setting and can be widened per analysis.
Why 15 minutes for software?Long enough for an install or a hang that builds up, short enough to keep a causal link. It never reaches past the previous power cycle; older events are still listed and summed up.
What does "App crashed · Possibly 25%" mean?An app crashed in that window and nothing stronger was found. 25% is the crash weight: an ordinary app crash cannot take Windows down, it shows what was failing. If the drive was failing too, 0.15 comes off — 10%.
How do you know who shut the PC down?User32 1074 records the process, the user, a reason code and a comment. The process maps to a category (Windows Update, vendor tool, IT management, user …) and the reason code is decoded from its bits, which are the same in every Windows language.
And if there is no 1074?Then "Not logged" — unless an installer, update or service says it restarted the PC (Likely) or an update was waiting for a restart (Possibly). Restart vs. shutdown then comes from the gap, flagged.
What is Storport, and how is it judged?Windows' storage port driver; its log records problems with individual I/O requests and usually names the drive. Its event IDs have no published meanings, so WELA uses Windows' own severity and lists information-level events with their fields without counting them.
How is the Samsung drive identified?By name, PCI vendor ID 144D or an MZ… part number in the event; by disk number through that boot's Partition inventory; or — marked "probably" — because it was the only drive.
What if the clock or time zone is wrong?Everything is compared in UTC; the display zone is a choice. Clock changes of 5 min or more are flagged with the process that made them, and time going backwards is flagged.
What if logs were cleared or records are missing?Both are detected (104 / 1102, record-ID gaps). Power cycles at a gap become Undetermined or lose 30% with a warning, and go to review.
Is customer data safe?It runs entirely on the engineer's PC, serves the UI on 127.0.0.1, makes no network calls and needs no installs.
Does it scale?196,400 events and 6,400 power cycles analyse in about 4.4 s on a laptop.
Why rules and not machine learning?Claim decisions need answers that are explainable and repeatable, and there is no labelled set of claims to train on yet. Rules can be audited line by line. AI fits on top — writing claim summaries from WELA's results — not in place of the rules.
Can the rules change without a developer?Yes: event IDs, weights, windows and vendor rules are data in the catalogue, overridable with wela_config.json; the main windows are also in the UI's settings.
Why "Possibly" so often?Because the logs rarely prove a software cause; WELA only says "Likely" or "Confirmed" when Windows recorded the request or the component said it restarted the PC.
What does it not do?No minidump analysis, no SMART import, one PC per case. Those are on the roadmap.
